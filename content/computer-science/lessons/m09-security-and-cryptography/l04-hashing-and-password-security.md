# Hashing and Password Security

Imagine you are checking your coat at a crowded theater. You hand over your expensive jacket, and in return, the attendant gives you a small, numbered plastic tag. That tag is not your jacket, and it cannot be turned back into your jacket by anyone. However, it is a unique identifier that proves you are the rightful owner. When you return at the end of the show, you present that tag, and the attendant uses it to find your specific item among hundreds of others. In the world of digital security, a hash function acts exactly like that plastic tag.

In our previous lesson, we explored how encryption allows two parties to scramble information so that only someone with the correct key can unscramble it. Encryption is a two-way process; it is designed to be reversed. Hashing, however, is a one-way street. A hash function takes an input of any size—a single word, a long document, or an entire digital library—and transforms it into a fixed-length string of characters that looks like random noise. Because the process is one-way, you cannot take the hash and mathematically work backward to reveal the original data. It is a digital fingerprint, not a lock and key.

This property makes hashing the standard for storing passwords. If you visit a website and create an account, that site should never store your actual password in its database. If the company were hacked, every user's password would be exposed in plain text, leading to a catastrophic security breach. Instead, when you sign up, the website passes your password through a hash function and stores only the resulting fingerprint. Each time you log in, the site takes the password you typed, runs it through the same hash function, and compares the new result to the one stored in its database. If the fingerprints match, the site knows you provided the correct password without ever needing to know what that password actually is.

Even with hashing, attackers can try to guess passwords by using lists of common words or previously leaked credentials. They hash these guesses and see if any match the fingerprints in a stolen database. To counter this, security engineers use a technique called salting. A salt is a random string of data added to your password before it is hashed. If your password is the word apple, the system might add a unique, random string to it before the hashing occurs. This creates a completely different fingerprint than a simple hash of the word apple would produce. Even if two users choose the same password, the unique salt ensures that their stored hashes will look entirely different. This forces an attacker to spend significantly more time and computing power to crack each individual entry, rather than using a single list to attack everyone at once.

Standard cryptographic hashes are designed to be extremely fast, which is great for verifying files but dangerous for passwords. Because they are fast, an attacker can test millions of guesses per second. To defend against this, we use specialized key derivation functions. These functions are intentionally designed to be slow and memory-intensive. By forcing the computer to perform a massive amount of work for every single password attempt, these functions make brute-force and dictionary attacks computationally impractical. Common examples of these slow functions include bcrypt, scrypt, and Argon two.

Of course, the strength of this defense also depends on the quality of the password you choose in the first place. A strong password should be long and complex enough to resist brute-force attacks, which are attempts to guess every possible combination of characters until one works. The longer the password, the more combinations an attacker must test, making the task computationally expensive. Ideally, a password should combine a mix of upper and lower case letters, numbers, and special symbols, or be a long, memorable passphrase that is difficult for a computer to predict. By choosing a high-entropy password, you significantly increase the work required for an attacker to find the original input, which is known as a preimage attack.

Hashing provides a robust way to verify your identity without exposing your secrets, but it is only the first layer of a larger security architecture. We have seen how we can store credentials safely, but we must also consider how systems confirm that the person presenting those credentials is truly who they claim to be. In our next lesson, we will examine the broader concepts of authentication and how we manage privacy in an interconnected world.

## Key ideas

- A one-way hash function converts data into a fixed-length fingerprint that cannot be reversed to reveal the original input.
- Websites store salted password hashes rather than plain text passwords to ensure that a database breach does not immediately expose user credentials.
- Password hashing should utilize slow, memory-hard key derivation functions to prevent attackers from testing millions of guesses per second.
- A salt is a random value added to a password before hashing to ensure that identical passwords result in unique stored fingerprints, which protects against large-scale guessing attacks.
- Password strength is determined by length and complexity, which increase the computational difficulty for an attacker attempting a preimage attack.
