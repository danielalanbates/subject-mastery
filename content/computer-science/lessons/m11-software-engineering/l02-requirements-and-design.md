# Requirements and Design

Imagine you are commissioned to build a massive bridge across a wide, turbulent river. You would not simply start pouring concrete into the water on the first day. You would first need to know if the bridge is intended for bicycles, heavy freight trucks, or high-speed passenger trains. You would need to study the soil conditions on the riverbanks, the expected wind speeds during storm seasons, and the total available budget. In the world of software engineering, this essential preparation is known as the phase of gathering requirements. It begins with the difficult, often subtle work of translating human needs into precise, written instructions that a technical team can actually execute.

Requirements act as the vital bridge between a vague business problem and a concrete technical solution. A client might tell you they want an application that makes their inventory management faster. To a software engineer, that is merely a wish, not a requirement. We must interview stakeholders to uncover specific constraints and hidden expectations. We document these as functional requirements, which describe exactly what the system must do, and non-functional requirements, which describe how the system must behave under pressure. Non-functional requirements cover critical attributes like performance, which is how fast the system responds; security, which is how it protects sensitive data; usability, which is how easily users can navigate the interface; reliability, which is how often the system stays available; and scalability, which is how well it handles growth as the user base expands. We validate these requirements by reviewing them with stakeholders to ensure they are accurate and complete, and we use traceability techniques to link each requirement to specific design elements and later test cases.

Once we have documented our requirements, we move into the phase of system design. If requirements tell us what we are building, design tells us how we will arrange the pieces to make the whole thing work. The primary goal here is to manage complexity. We use decomposition to break the entire system into smaller, manageable modules. Architects often choose a specific style to guide this process, such as a layered style, where components are organized into distinct tiers; a client-server style, where tasks are split between providers and requesters; or a microservices style, where the system is composed of many small, independent, and loosely coupled services.

The secret to successful design is creating clear, reliable interfaces. An interface is essentially a formal contract between two parts of a system. It defines how one module asks for information from another and exactly what it expects in return. The internal logic of the module is hidden, allowing the team to change the code later without breaking other parts of the application. This relies on the principle of encapsulation, which hides internal workings to reduce the chance that a change in one area causes unexpected errors elsewhere.

When designing, we must constantly balance cohesion and coupling. Cohesion measures how closely related the responsibilities within a single module are. We want high cohesion, where a module does one thing and does it very well. Coupling measures how dependent modules are on one another. We want low coupling so that modules remain independent and easy to replace. If two modules need to know the intimate details of how the other works, they are too tightly coupled, and the design needs simplifying. By focusing on these boundaries, we prevent the software from becoming a tangled, fragile web of dependencies.

We decide which modules handle data storage, which handle user input, and how they exchange messages across the network. This is a process of balancing constant trade-offs. We decide which parts need to be extremely fast, which need to be highly flexible, and which need to be secure against external threats. A well-designed system is one where the boundaries between components are obvious, logical, and easy to understand. This foresight is what separates a fragile prototype from a robust, industrial-strength software product that can grow and thrive over many years. By defining these structures early, we ensure the system remains maintainable even as the project evolves and the business requirements change. Good design is not just about making things work today; it is about making sure the system can survive the demands of tomorrow.

## Key ideas

- Requirements translate vague user needs into specific functional and non-functional goals, which are validated through stakeholder review and linked via traceability.
- System design manages complexity by using architectural styles like layered or microservices to organize the system into manageable, cohesive modules.
- An interface acts as a formal contract that defines how different modules communicate, allowing them to interact without knowing each other's internal details.
- High cohesion and low coupling ensure that modules remain independent and maintainable, preventing changes in one area from breaking the entire system.
