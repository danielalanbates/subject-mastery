# Fractions and Floating Point

Imagine you are trying to measure a piece of wood with a ruler that only has markings for whole inches. You can measure a board that is exactly five inches long, but what happens when you need to measure a piece that is five and a half inches? In our last lesson, we looked at how computers use binary to represent whole numbers. We saw that when these numbers grow too large, we encounter overflow. But the real world is rarely made of neat, whole units. To represent values like half, a quarter, or the precise measurement of a scientific constant, computers need a way to handle fractions.

The most common way computers handle these non-integer values is through a system called floating point. Think of floating point as a binary version of scientific notation. In decimal, we write large or small numbers by keeping a significant part of the number, called the significand, and multiplying it by a power of ten. For example, the speed of light is roughly three times ten to the power of eight. In binary, we do the same thing, but we use powers of two. The computer splits a fixed amount of space—usually thirty-two or sixty-four bits—into three distinct sections. One bit indicates the sign, which tells us if the number is positive or negative. A group of bits acts as the exponent, determining where the binary point should float. The remaining bits store the significand.

To maximize the range of numbers we can represent, the exponent is stored with a bias. This bias is a fixed value subtracted from the stored exponent, allowing the system to represent both very large positive exponents and very small negative exponents without needing a separate sign bit for the exponent itself. Furthermore, to save space, floating point systems use an implicit leading bit. In a normalized number, the first digit of the significand is always a one. Because this is always true, the computer does not actually store that leading one. It assumes it is there, which effectively gives the computer one extra bit of precision for free.

This system is powerful because it allows a computer to represent an incredibly wide range of values using the same amount of memory. However, this flexibility comes with a hidden cost. Because we are trying to map base ten fractions into a base two system, we run into a fundamental problem of representation.

In our decimal system, we can easily write one tenth as zero point one. It looks simple, but try to represent that same value in binary. In base ten, a fraction is a sum of powers of ten. In binary, a fraction must be a sum of negative powers of two. That means we are adding halves, quarters, eighths, sixteenths, and so on. When you try to build one tenth using only these fractions, you find that you cannot reach it exactly. It is like trying to pay exactly one dollar using only three-cent coins; no matter how many you stack, you will never hit the target precisely.

Because the computer has a finite number of bits to store this value, it eventually has to stop adding up these fractions. It takes the closest possible approximation it can manage and rounds off the rest. This leads to what we call rounding errors. If you tell a computer to add one tenth to itself ten times, you might expect the result to be exactly one. Instead, because of those tiny, invisible rounding errors, the computer might store the result as a value that is just slightly different from one, such as zero point nine nine nine followed by a long string of nines.

These errors are usually so small that they do not matter for everyday tasks like drawing graphics or playing music. Money is a special case: because even a stray fraction of a cent is unacceptable, banking software usually stores amounts as whole numbers of cents or uses special decimal number types rather than binary floating point. However, in high-stakes fields like aerospace engineering, meteorology, or financial modeling, these tiny discrepancies can compound. If a program performs millions of calculations, those microscopic errors can grow into significant inaccuracies. This is why programmers must be careful when comparing two floating point numbers for equality. Checking whether a computed result, such as three tenths minus two tenths, is exactly equal to one tenth will often return false, because the computer sees a slightly different number than the one you intended.

Understanding these limits is a vital part of writing robust software. We accept that our digital representations of the world are approximations, and we design our algorithms to account for that reality. By recognizing that some numbers are fundamentally incompatible with binary storage, we can better anticipate where our calculations might drift. Once we have mastered how computers represent these numeric values, we can move on to how they handle the characters and symbols that make up the written words we use to communicate.

## Key ideas

- Floating point represents non-integer numbers using a binary version of scientific notation consisting of a sign, a biased exponent, and a significand.
- The implicit leading bit technique assumes the first digit of the significand is always one, allowing for greater precision within the same amount of memory.
- Computers struggle to represent some simple decimal fractions because they cannot be expressed as a finite sum of negative powers of two.
- Because memory is limited, computers must round these values, which introduces tiny, persistent inaccuracies known as rounding errors that can accumulate during complex calculations.
- Programmers should avoid comparing floating point numbers for exact equality, as rounding errors often make two values that should be identical appear slightly different.
