# Objects and Classes

Imagine you are looking at a bustling coffee shop. You see several different machines behind the counter. There is an espresso maker, a coffee grinder, and a blender. Each of these machines has its own internal components, like heating elements or spinning blades, and each machine performs a specific set of tasks. You do not need to know exactly how the heating element inside the espresso maker works to get a cup of coffee. You simply interact with the machine through a standard set of buttons or levers. In programming, we use a similar concept to organize complex systems. We call these entities objects.

In our previous lesson, we looked at functions and parameters as a way to bundle logic into reusable units. Functions are excellent for performing calculations or transforming data, but they often operate on data that lives somewhere else. An object takes this a step further by bundling the data and the actions together into one self-contained package. Think of an object as a digital container that holds both the information about a specific thing and the tools needed to manipulate that information. If we were building a program to manage a bank, an account would be an object. It would hold the balance and the account number as its data, and it would bundle the actions to deposit or withdraw money right alongside that data.

Because we often need many similar items in a program, we need a way to create these objects efficiently. We do not want to define every single bank account from scratch every time we need a new one. This is where the concept of a class comes in. A class acts as a blueprint or a template. If an object is the actual house you live in, the class is the architectural drawing that defines how many rooms it has and where the doors go. The blueprint itself is not a house; you cannot live in a drawing. But using that blueprint, a builder can construct as many houses as needed, each with its own unique address and residents, while all following the same structural rules.

When we create an object from a class, we are essentially stamping out a new instance based on that blueprint. Every object created from the same class will have the same categories of data, such as a balance and an account number, but the specific values stored inside those categories will be different for every individual object. One account object might have a balance of five hundred dollars, while another has a balance of zero. The class ensures that every account has a place to store a balance, but the object itself holds the actual number.

This approach of bundling data and actions is known as encapsulation. It is a powerful way to manage complexity because it hides the internal details of an object from the rest of the program. If you are writing a program that calculates total interest across all bank accounts, you do not need to worry about how the withdrawal function works internally. You only need to know that the account object provides a way to access the balance. This separation of concerns means that if the bank decides to change the way it calculates interest, you can update the logic inside the class without breaking the other parts of the program that rely on those account objects.

Consider a game featuring a fleet of spaceships. You could write a class called spaceship that defines the common traits of every ship, such as its hull strength, its current speed, and its position in space. You would also define the actions that every ship can perform, such as moving forward, turning, or taking damage. Once you have this spaceship class, you can create one hundred individual spaceship objects with just a few lines of instructions. Each object maintains its own unique speed and position, but they all share the same logic for how to move or how to react when they are hit.

Using classes and objects allows programmers to model the world in a way that feels intuitive. We start by identifying the real-world things our program needs to represent, defining the blueprints for those things, and then creating as many instances of those things as the program requires. This structure makes our code easier to read, easier to test, and much simpler to expand as our needs grow. Understanding how we package these concepts is the final step in mastering the basic building blocks of modern software. Once we understand how to structure our data and logic into these organized units, we can begin to explore how these programs are translated into instructions that the computer can actually execute.

## Key ideas

- An object is a self-contained unit that bundles together data and the specific actions that can be performed on that data.
- A class serves as a blueprint or template that defines the structure and behavior for all objects created from it.
- Encapsulation is the practice of hiding the internal workings of an object and only exposing the necessary tools to interact with it.
- Classes allow developers to create many unique, independent objects that all follow the same consistent rules for data and behavior.
